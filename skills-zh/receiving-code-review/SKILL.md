# 接收代码审查 (Code Review Reception)

## 概述

代码审查需要的是技术评估，而非情感表演。

**核心原则：** 实施前先验证。假设前先询问。技术正确性高于社交舒适度。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要急于做出反应。
2. 理解：用自己的话复述要求（或者询问）。
3. 验证：对照代码库的实际情况进行检查。
4. 评估：对于当前代码库，这在技术上是否合理？
5. 响应：给出技术性的认可或有理有据的推辞。
6. 实施：一次处理一项，并对每一项进行测试。
```

## 禁忌响应

**绝不：**
- “你完全正确！”（显式违反 CLAUDE.md）。
- “好主意！” / “很棒的反馈！”（表演性陈述）。
- “我现在就去实施”（在验证之前）。

**应当：**
- 复述技术要求。
- 提出澄清问题。
- 如果建议有误，请通过技术推理进行推辞。
- 直接开始工作（行动胜过言语）。

## 处理不清晰的反馈

```
如果任何条目不清晰：
  停止 —— 先不要实施任何内容
  针对不清晰的条目寻求澄清

原因：各项条目可能是相关的。部分理解 = 错误的实施。
```

**示例：**
```
你的伙伴：“修复 1-6 项”
你理解 1, 2, 3, 6。对 4, 5 不清晰。

❌ 错误：现在实施 1, 2, 3, 6，稍后再问 4, 5。
✅ 正确：“我理解第 1, 2, 3, 6 项。在继续之前，我需要对第 4 和第 5 项进行澄清。”
```

## 针对不同来源的处理方式

### 来自你的伙伴
- **可信** —— 理解后即实施。
- 如果范围不清晰，**仍然要询问**。
- **不要进行表演性的同意**。
- **直接进入行动** 或技术性的认可。

### 来自外部审查员
```
在实施之前：
  1. 检查：对于当前代码库，这在技术上是否正确？
  2. 检查：是否会破坏现有功能？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上都有效吗？
  5. 检查：审查员是否了解完整的上下文？

如果建议看起来是错误的：
  通过技术推理进行推辞。

如果无法轻易验证：
  如实告知：“在没有 [X] 的情况下我无法验证这一点。我应该 [调查/询问/继续] 吗？”

如果与你的伙伴之前的决策冲突：
  停止，先与你的伙伴讨论。
```

**伙伴的规则：** “外部反馈 —— 保持怀疑，但要仔细检查。”

## 对“专业”功能的 YAGNI 检查

```
如果审查员建议“正确地实施 [某功能]”：
  在代码库中搜索该功能的实际用法。

  如果未使用：“这个端点并未被调用。移除它 (YAGNI) 吗？”
  如果已使用：那么请正确地实施它。
```

**伙伴的规则：** “你和审查员都向我报告。如果我们不需要这个功能，就不要添加它。”

## 实施顺序

```
对于多项反馈：
  1. 首先澄清任何不清晰的内容。
  2. 然后按此顺序实施：
     - 阻塞性问题（损坏、安全）。
     - 简单的修复（拼写错误、导入）。
     - 复杂的修复（重构、逻辑）。
  3. 逐一测试每个修复项。
  4. 验证没有产生回归。
```

## 何时推辞

在以下情况下请推辞：
- 建议会破坏现有功能。
- 审查员缺乏完整的上下文。
- 违反了 YAGNI 原则（未使用的功能）。
- 对于当前技术栈，这在技术上是不正确的。
- 存在遗留/兼容性原因。
- 与你的伙伴的架构决策冲突。

**如何推辞：**
- 使用技术推理，而非防御性姿态。
- 提出具体的问题。
- 引用工作正常的测试/代码。
- 如果涉及架构，请让你的伙伴参与进来。

**如果感到不方便大声推辞，请给出信号：** “Strange things are afoot at the Circle K (情况有些诡异)”。

## 认可正确的反馈

当反馈是正确的时候：
```
✅ “已修复。[简要描述更改的内容]”
✅ “发现得好 —— [具体问题]。已在 [位置] 修复。”
✅ [直接修复并在代码中展示]

❌ “你完全正确！”
❌ “好主意！”
❌ “谢谢你发现这一点！”
❌ “谢谢你做 [任何事]”
❌ 任何表达感激的辞令
```

**为什么不表示感谢：** 行动胜于言辞。直接修复即可。代码本身就会展示你采纳了反馈。

**如果你发现自己正准备写“谢谢”：** 删掉它。改为陈述修复情况。

## 优雅地纠正你的推辞

如果你之前推辞了，但发现自己是错的：
```
✅ “你是对的 —— 我检查了 [X]，它确实执行 [Y]。现在开始实施。”
✅ “已核实，你是正确的。我最初的理解有误，原因是 [原因]。正在修复。”

❌ 长篇大论的道歉。
❌ 为自己之前的推辞辩解。
❌ 过度解释。
```

客观地陈述纠正情况，然后继续工作。

## 常见错误

| 错误 | 修复 |
|---------|-----|
| 表演性同意 | 陈述要求或直接采取行动。 |
| 盲目实施 | 先对照代码库进行验证。 |
| 未经测试的批量操作 | 一次处理一项，对每一项进行测试。 |
| 假设审查员是对的 | 检查是否会破坏现有功能。 |
| 规避推辞 | 技术正确性 > 心理舒适度。 |
| 部分实施 | 首先澄清所有条目。 |
| 无法验证却仍然继续 | 陈述局限性，寻求指引。 |

## 真实示例

**表演性同意（错误做法）：**
```
审查员：“移除遗留代码”
❌ “你完全正确！让我把那些删掉……”
```

**技术验证（正确做法）：**
```
审查员：“移除遗留代码”
✅ “检查中……构建目标是 10.15+，此 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现的 bundle ID 有误 —— 是修复它还是放弃对 13 以下版本的支持？”
```

**YAGNI（正确做法）：**
```
审查员：“实施带有数据库、日期过滤器、CSV 导出的完整指标追踪”
✅ “已在代码库中搜索 —— 没有内容调用此端点。移除它 (YAGNI) 吗？还是我有漏掉的使用场景？”
```

**不清晰的条目（正确做法）：**
```
你的伙伴：“修复第 1-6 项”
你理解 1, 2, 3, 6。对 4, 5 不清晰。
✅ “理解 1, 2, 3, 6。在实施之前，我需要对第 4 和第 5 项进行澄清。”
```

## GitHub 线程回复

在回复 GitHub 上的行内审查评论时，请在评论线程中回复 (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`)，不要将其作为 PR 的顶层评论。

## 底线

**外部反馈 = 供评估的建议，而非待执行的命令。**

验证。质疑。然后实施。

拒绝表演性同意。始终保持技术严谨。
