# 系统化调试 (Systematic Debugging)

## 概述

随意的修复会浪费时间并产生新的 bug。快速的补丁只会掩盖底层问题。

**核心原则：** 在尝试修复之前，**务必** 找到根本原因。只修复症状是失败的。

**违反此流程的具体步骤即是违反调试的精神。**

## 铁律

```
在进行根因调查之前，严禁尝试任何修复
```

如果你还没有完成第一阶段，你就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**在以下情况下尤其要使用：**
- 处于时间压力下（紧急情况往往会让猜测变得诱人）
- “只需一个快速修复”看起来很明显
- 你已经尝试了多种修复方法
- 之前的修复没起作用
- 你不完全理解该问题

**在以下情况下也不要跳过：**
- 问题看起来很简单（简单的 bug 也有根本原因）
- 你很匆忙（仓促行事保证了会有返工）
- 经理想要立即修复（系统化比盲目折腾更快）

## 四个阶段

你必须完成每个阶段后再进入下一个阶段。

### 第一阶段：根因调查 (Root Cause Investigation)

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要略过错误或警告。
   - 它们通常包含确切的解决方案。
   - 完整阅读堆栈跟踪。
   - 记录行号、文件路径、错误代码。

2. **保持一致性复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 是否每次都会发生？
   - 如果不可复现 → 收集更多数据，不要猜测。

3. **检查近期变更**
   - 发生了什么可能导致此问题的变更？
   - 查看 Git diff、近期提交。
   - 新的依赖项、配置更改。
   - 环境差异。

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断性监测 (instrumentation)：**
   ```
   针对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播情况
     - 检查每一层的状态

   运行一次以收集显示故障发生地点的证据
   然后分析证据以识别故障组件
   然后对该特定组件进行调查
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流 (Workflow)
   echo "=== 工作流中可用的秘密 (Secrets): ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本 (Build script)
   echo "=== 构建脚本中的环境变量: ==="
   env | grep IDENTITY || echo "环境变量中没有 IDENTITY"

   # 第 3 层：签名脚本 (Signing script)
   echo "=== 钥匙串状态: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层发生了故障（secrets → workflow ✓, workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈中时：**

   请参阅本目录下的 `root-cause-tracing.md`，了解完整的向后追踪技术。

   **快速版本：**
   - 错误值源自何处？
   - 是什么调用了带有该错误值的方法/函数？
   - 向上持续追踪，直到找到源头。
   - 在源头修复，而非在症状处修复。

### 第二阶段：模式分析 (Pattern Analysis)

**在修复之前找到模式：**

1. **寻找工作正常的示例**
   - 在同一个代码库中定位类似的正常运行的代码。
   - 有哪些与损坏代码类似但工作正常的代码？

2. **对比参考资料**
   - 如果在实现某种模式，请完整阅读参考实现。
   - 不要略读 —— 阅读每一行。
   - 在应用之前完全理解该模式。

3. **识别差异**
   - 工作正常和损坏的代码之间有什么区别？
   - 列出每一个细微的区别。
   - 不要假设“那没关系”。

4. **理解依赖关系**
   - 此组件还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与测试 (Hypothesis and Testing)

**科学方法：**

1. **形成单一假设**
   - 清晰地陈述：“我认为 X 是根本原因，因为 Y”。
   - 把它写下来。
   - 保持具体，不要模糊。

2. **进行最小化测试**
   - 进行尽可能小的更改来测试假设。
   - 一次只改变一个变量。
   - 不要同时修复多件事。

3. **在继续之前进行验证**
   - 起作用了吗？是 → 进入第四阶段。
   - 没起作用？形成新的假设。
   - 不要在此之上叠加更多修复。

4. **当你不知道时**
   - 说“我不理解 X”。
   - 不要不懂装懂。
   - 寻求帮助。
   - 进行更多研究。

### 第四阶段：实施 (Implementation)

**修复根本原因，而非症状：**

1. **创建失败的测试用例**
   - 最简单的复现方式。
   - 尽可能使用自动化测试。
   - 如果没有框架，使用一次性测试脚本。
   - 修复前必须拥有。
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试。

2. **实施单一修复**
   - 解决已识别的根本原因。
   - 一次只做一个变更。
   - 不要进行“顺便”的改进。
   - 不要捆绑重构。

3. **验证修复**
   - 现在测试通过了吗？
   - 没有破坏其他测试吧？
   - 问题真的解决了吗？

4. **如果修复不起作用**
   - 停止。
   - 计数：你已经尝试了多少次修复？
   - 如果 < 3：返回第一阶段，根据新信息重新分析。
   - **如果 ≥ 3：停止并质疑架构（见下方的步骤 5）。**
   - 在进行架构讨论之前，不要尝试第 4 次修复。

5. **如果 3 次以上的修复都失败了：质疑架构**

   **预示架构问题的模式：**
   - 每次修复都在不同地方揭示了新的共享状态/耦合/问题。
   - 修复需要进行“大规模重构”才能实施。
   - 每次修复都会在其他地方产生新的症状。

   **停止并质疑基本面：**
   - 这个模式从根本上说是可靠的吗？
   - 我们是否仅仅因为“惯性”而坚持使用它？
   - 我们是否应该重构架构，而非继续修复症状？

   **在尝试更多修复之前与你的伙伴讨论。**

   这本身不是一个失败的假设 —— 这是一个错误的架构。

## 红旗信号 —— 停止并遵循流程

如果你发现自己有以下想法：
- “先快速修复，稍后调查。”
- “试着改一下 X 看看是否起作用。”
- “添加多项更改，运行测试。”
- “跳过测试，我会手动验证。”
- “可能是 X，让我修复它。”
- “我不完全理解，但这可能会起作用。”
- “模式说是 X，但我会以不同方式适配它。”
- “这里有几个主要问题：[在未调查的情况下列出修复方案]”
- 在追踪数据流之前提出解决方案。
- **“再试一次修复”（当已经尝试了 2 次以上时）。**
- **每次修复都在不同地方揭示新问题。**

**所有这些都意味着：停止。返回第一阶段。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）。

## 伙伴发出的信号：你做错了

**注意以下重定向信号：**
- “那是没有发生吗？” —— 你未经核实就做了假设。
- “它会向我们展示……吗？” —— 你应该增加证据收集。
- “不要猜” —— 你在不理解的情况下提出修复建议。
- “深度思考 (Ultrathink) 这一点” —— 质疑基本面，而非仅仅是症状。
- “我们卡住了？”（感到沮丧） —— 你的方法不起作用。

**当你看到这些信号时：** 停止。返回第一阶段。

## 常见的借口

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单的问题也有根本原因。对于简单的 bug，流程运行很快。 |
| “情况紧急，没时间走流程” | 系统化调试比猜测试错的折腾更快。 |
| “先试一下这个，然后再调查” | 第一次修复就确立了模式。从一开始就做对。 |
| “确认修复有效后再写测试” | 未经测试的修复站不住脚。先写测试能证明它。 |
| “同时进行多个修复能节省时间” | 无法隔离出起作用的部分。会引发新的 bug。 |
| “参考资料太长，我会自己适配模式” | 局部理解保证了会出 bug。请完整阅读。 |
| “我看到问题了，让我修复它” | 看到症状 ≠ 理解根本原因。 |
| “再试一次修复”（失败 2 次以上后） | 3 次以上失败 = 架构问题。质疑模式，不要再修复了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 寻找工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、进行最小化测试 | 确认假设或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 已解决，测试通过 |

## 当流程显示“没有根本原因”时

如果系统化的调查显示问题确实源于环境、时序依赖或外部因素：

1. 你已经完成了流程。
2. 记录你调查的内容。
3. 实施适当的处理方法（重试、超时、错误信息）。
4. 为未来的调查添加监控/日志。

**但是：** 95% 的“没有根本原因”案例实际上是调查不完整。

## 支持技术

这些技术是系统化调试的一部分，可在本目录下找到：

- **`root-cause-tracing.md`** —— 通过调用栈向后追踪 bug 以找到原始触发点。
- **`defense-in-depth.md`** —— 找到根本原因后，在多个层级添加验证。
- **`condition-based-waiting.md`** —— 使用条件轮询取代随意的超时 (timeout)。

**相关技能：**
- **superpowers:test-driven-development** —— 用于创建失败的测试用例（第四阶段，第 1 步）。
- **superpowers:verification-before-completion** —— 在声称成功之前验证修复是否有效。

## 现实影响

来自调试会话的数据：
- 系统化方法：15-30 分钟修复。
- 随机修复方法：2-3 小时的盲目折腾。
- 首次修复成功率：95% vs 40%。
- 引入的新 bug：接近零 vs 常见。
