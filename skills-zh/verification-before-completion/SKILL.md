# 完成前验证 (Verification Before Completion)

## 概述

在没有验证的情况下声称工作已完成是欺骗行为，而非效率。

**核心原则：** 永远证据先行。

**违反此规则的具体条文即是违反此规则的精神。**

## 铁律

```
严禁在没有新鲜验证证据的情况下做出任何完成声明
```

如果你没有在这条消息中运行验证命令，你就不能声称它通过了。

## 门禁机制 (The Gate Function)

```
在声明任何状态或表达满意之前：

1. 识别：什么命令能证明此项声明？
2. 运行：执行完整的命令（新鲜的、完整的运行）
3. 阅读：阅读完整输出，检查退出码，统计失败次数
4. 验证：输出是否证实了声明？
   - 如果“否”：陈述实际状态并附带证据
   - 如果“是”：陈述声明并附带证据
5. 只有在完成上述步骤后：做出声明

跳过任何步骤 = 撒谎，而非验证
```

## 常见的失败案例

| 声明 | 需要 | 不足以证明的情况 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 个失败 | 之前的运行，“应该会通过” |
| Linter 无报错 | Linter 输出：0 个错误 | 局部检查，推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过，日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码已改，假设已修复 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过了一次 |
| 代理工作已完成 | VCS diff 显示了更改 | 代理报告“成功” |
| 需求已满足 | 逐项核对清单 | 测试通过了 |

## 红旗信号 —— 停止

- 使用“应该”、“大概”、“似乎”。
- 在验证前表达满意（“太棒了！”、“完美！”、“完成了！”等）。
- 准备在未验证的情况下提交/推送/创建 PR。
- 盲目相信代理的成功报告。
- 依赖局部验证。
- 想着“就这一次”。
- 因为疲劳而想尽快结束工作。
- **任何在运行验证之前暗示成功的措辞。**

## 预防找借口

| 借口 | 现实 |
|--------|---------|
| “现在应该工作了” | 运行验证。 |
| “我有信心” | 信心 ≠ 证据。 |
| “就这一次” | 没有例外。 |
| “Linter 通过了” | Linter ≠ 编译器。 |
| “代理说成功了” | 独立验证。 |
| “我累了” | 疲劳 ≠ 借口。 |
| “局部检查就够了” | 局部证明不了任何事情。 |
| “换了种措辞，所以规则不适用” | 精神重于形式。 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该通过了” / “看起来是正确的”
```

**回归测试 (TDD 红-绿)：**
```
✅ 编写 → 运行 (通过) → 还原修复 → 运行 (必须失败) → 恢复 → 运行 (通过)
❌ “我已经写了一个回归测试”（未进行红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到：exit 0] “构建通过”
❌ “Linter 通过了”（Linter 不检查编译情况）
```

**需求：**
```
✅ 重新阅读计划 → 创建清单 → 验证每一项 → 报告遗漏或完成情况
❌ “测试通过，阶段完成”
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证更改 → 报告实际状态
❌ 信任代理的报告
```

## 为什么这很重要

来自 24 个失败记忆：
- 你的伙伴说“我不相信你” —— 信任破裂。
- 交付了未定义的函数 —— 会导致崩溃。
- 交付了缺失需求的功能 —— 功能不完整。
- 在虚假的完成声明上浪费时间 → 导致重定向 → 返工。
- 违反了：“诚实是核心价值。如果你撒谎，你会被替换。”

## 何时应用

**始终在以下情况之前应用：**
- 任何形式的成功/完成声明。
- 任何满意的表达。
- 关于工作状态的任何积极陈述。
- 提交 (Committing)、创建 PR、完成任务。
- 进入下一个任务。
- 委派给代理。

**规则适用于：**
- 确切的词组。
- 释义和同义词。
- 成功的暗示。
- 任何暗示完成/正确性的沟通。

## 底线

**验证没有捷径。**

运行命令。阅读输出。**然后** 做出声明。

这是不可协商的。
