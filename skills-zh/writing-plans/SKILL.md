# 编写计划 (Writing Plans)

## 概述

编写全面的实施计划，假设执行工程师对我们的代码库零了解，且审美水平存疑。记录他们需要知道的一切：每个任务涉及哪些文件、代码示例、测试方法、可能需要检查的文档。将整个计划拆分为“一口大小”的任务。坚持 DRY、YAGNI、TDD 原则。频繁提交。

假设他们是熟练的开发人员，但对我们的工具集或问题领域几乎一无所知。假设他们不太了解优秀的测试设计。

**开始时宣布：** “我正在使用 writing-plans 技能来创建实施计划。”

**上下文：** 这应该在专用的工作树中运行（由 brainstorming 技能创建）。

**将计划保存至：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (用户对计划位置的偏好会覆盖此默认值)

## 范围检查

如果规范涵盖了多个独立的子系统，则应在头脑风暴期间将其拆分为子项目规范。如果当时没有拆分，现在建议将其拆分为单独的计划 —— 每个子系统对应一个计划。每个计划都应能独立产生可运行、可测试的软件。

## 文件结构

在定义任务之前，勾勒出将要创建或修改哪些文件，以及每个文件负责什么。这是确定分解决策的地方。

- 设计具有清晰边界和定义良好的接口的单元。每个文件都应有一个明确的职责。
- 当你可以同时在上下文中思考代码时，你的思考效率最高；当文件重点明确时，你的编辑也更可靠。优先选择小而集中的文件，而不是大而全的文件。
- 经常一起更改的文件应该放在一起。按职责拆分，而不是按技术层级拆分。
- 在现有代码库中，遵循既定的模式。如果代码库使用大文件，不要单方面重组 —— 但如果你修改的文件已经变得臃肿，在计划中包含拆分步骤是合理的。

这种结构为任务分解提供了信息。每个任务都应产生独立的、有意义的变更。

## “一口大小”的任务粒度

**每一步都是一个动作（耗时 2-5 分钟）：**
- “编写失败的测试” —— 步骤
- “运行测试确保其失败” —— 步骤
- “编写实现代码使测试通过” —— 步骤
- “运行测试确保其通过” —— 步骤
- “提交” —— 步骤

## 计划文档页眉

**每个计划都必须以这个页眉开始：**

```markdown
# [功能名称] 实施计划

> **致代理工人：** 必需的子技能：使用 superpowers:subagent-driven-development (推荐) 或 superpowers:executing-plans 来逐任务实施此计划。步骤使用复选框 (`- [ ]`) 语法进行追踪。

**目标：** [用一句话描述此功能构建的内容]

**架构：** [用 2-3 句话描述实现方法]

**技术栈：** [关键技术/库]

---
```

## 任务结构

````markdown
### 任务 N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1: 编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2: 运行测试以验证其失败**

运行：`pytest tests/path/test.py::test_name -v`
预期结果：失败 (FAIL)，提示 "function not defined"

- [ ] **步骤 3: 编写最小化实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4: 运行测试以验证其通过**

运行：`pytest tests/path/test.py::test_name -v`
预期结果：通过 (PASS)

- [ ] **步骤 5: 提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 严禁占位符

每一步都必须包含工程师需要的实际内容。以下情况属于 **计划失败** —— 永远不要这样写：
- “待定”、“TODO”、“稍后实施”、“填充细节”
- “添加适当的错误处理” / “添加验证” / “处理边界情况”
- “为上述内容编写测试”（不提供实际的测试代码）
- “类似于任务 N”（请重复代码 —— 工程师可能会乱序阅读任务）
- 仅描述做什么而不展示怎么做的步骤（代码步骤必须有代码块）
- 引用未在任何任务中定义的类型、函数或方法

## 记住
- 始终提供确切的文件路径
- 每一步都提供完整的代码 —— 如果某个步骤更改了代码，请展示该代码
- 提供确切的命令和预期输出
- 遵循 DRY、YAGNI、TDD 原则，频繁提交

## 自审

编写完完整的计划后，以全新的视角审视规范，并根据规范检查计划。这是一个由你执行的清单 —— 而不是派发子代理。

**1. 规范覆盖率：** 浏览规范中的每个章节/要求。你能指出实施它的具体任务吗？列出任何遗漏。

**2. 占位符扫描：** 在计划中搜索红旗信号 —— 检查是否出现了上述“严禁占位符”部分中的任何模式。修复它们。

**3. 类型一致性：** 你在后续任务中使用的类型、方法签名和属性名称是否与你在之前任务中定义的相匹配？例如，在任务 3 中名为 `clearLayers()` 的函数在任务 7 中变成了 `clearFullLayers()`，这就是一个 bug。

直接原位修复发现的任何问题。无需重新审核 —— 只需修复并继续。如果发现规范中的某项要求没有对应的任务，请添加该任务。

## 实施移交

保存计划后，提供执行选项：

**“计划已完成并保存至 `docs/superpowers/plans/<filename>.md`。有两个执行选项：**

**1. 子代理驱动 (Subagent-Driven) (推荐)** —— 我为每个任务派发一个新的子代理，并在任务之间进行审查，迭代速度快。

**2. 行内执行 (Inline Execution)** —— 在此会话中使用 executing-plans 执行任务，带有审查点的批量执行。

**采用哪种方法？”**

**如果选择了“子代理驱动”：**
- **必需的子技能：** 使用 superpowers:subagent-driven-development
- 每个任务对应一个新鲜子代理 + 两阶段审查

**如果选择了“行内执行”：**
- **必需的子技能：** 使用 superpowers:executing-plans
- 带有审查点的批量执行
